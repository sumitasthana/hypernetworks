Running UnCLe on Colab

How to run it, then what the paper actually measured and how to reproduce each piece, with what every run costs in time and GPU memory. One package, uncle: the task streams, the hypernetwork, the learn and forget operations, and the four numbers the paper reports.

Setup

Three cells, once per runtime. Runtime → Change runtime type → T4 GPU before you start, otherwise everything below runs on a CPU and the ResNet runs are hopeless.

1Clone and install, once per runtime
Do not pip install -r requirements.txt here. Colab already ships torch, torchvision, numpy, Pillow, matplotlib and tqdm, and reinstalling torch is the fastest way to get a build that cannot see the GPU. That file is for a local machine. tqdm is the only optional one: without it the progress bars quietly turn off and everything else works.
If you see ModuleNotFoundError: No module named 'uncle', re-run the cell above. That is nearly always the whole story, and the cell is safe to run any number of times.

Two things make this happen more often than it should, and the cell is built against both. sys.path.insert does not survive Runtime → Restart session, so a restart quietly un-finds the package; pip install -e registers it properly and os.chdir puts the repository root on the path regardless, because IPython keeps the working directory there. And Colab wipes /content when a runtime is recycled or deleted, which takes the clone with it. sys.path.insert never checks that the directory exists, so the path can look perfectly correct while pointing at nothing at all: that is why the cell ends by importing the package and printing where it came from. It either works there or it fails there, instead of three cells later.

--no-deps stops pip reaching for torch, which Colab already has and which you do not want reinstalled.

Why importlib.invalidate_caches() is in there. Without it the cell can clone the repository, install it, change directory into it, and still fail on import uncle with the files plainly visible in the file browser. When a path is added to sys.path before the directory exists, Python caches the fact that nothing importable lives there, and goes on trusting that cache after the directory appears. The same applies to the .pth file an editable install drops into site-packages, which is read when the interpreter starts. One call clears both. Restarting the runtime also clears it, but then you have to remember to re-run this cell first, which is the loop that caused the trouble in the first place.

Two names that look alike and are not. uncle.experiments (plural) is the front door, and holds run_experiment, run_sequences and make_config. uncle.experiment (singular) is the request loop underneath, and holds run, which takes a finished Config. Importing run_experiment from the singular one fails.

If anything looks stale, pull and restart. !git -C /content/hypernetworks pull, then Runtime → Restart session. A pull on its own is not enough once a cell has imported anything, because Python keeps the old modules in memory. That surfaces later as a confusing TypeError or an unexpected signature, not as an import error.
2Confirm the GPU is really there

Every entry point picks cuda on its own when it is available, so there is nothing to pass. If this prints False, stop and fix the runtime type.

3Dataset on local disk, results on Drive

Pass root=DATA, download=True on the first call of a session. The dataset is 240 MB and re-downloads each time the runtime is recycled, which takes about a minute.

Do not put the dataset on Drive. It is tempting, because then the download happens once instead of once per session. But Tiny ImageNet is 120,000 small files, and extracting that through Drive's mount is slow and stalls often. A stall leaves the directory in place but incomplete, which used to produce a particularly unhelpful failure: the code checked only whether the directory existed, so it skipped the repair and then reported the dataset as missing while telling you to pass download=True, which you already had. It now checks whether the dataset is complete, and repairs a partial copy. Still, keep the dataset local and Drive for results, which are a handful of small JSON files and exactly what a mounted drive is good at.

If you have a half-extracted copy on Drive from before, point DATA at local disk as above and it will be ignored. Deleting it is optional.

Example 1: the smoke test

Run this before anything expensive. It uses the small stand-in network, 32 chunks, one epoch, the first five requests and 300 images per task, so it finishes in minutes and proves the whole path works: partition, data, hypernetwork, learn, forget, metrics. Cell 3 is optional for this one: without root, the dataset downloads into the clone and goes away with the runtime.

4minutes

You get one line per request as it lands:

Read the trailing numbers as task:accuracy. Do not expect much from one epoch on 300 images: what matters here is that request 2 pushed task 3 down and left the others roughly where they were.

Fixed: the classifier's initialization. If you ran this before 21 September 2025, re-pull. The cnn backbone could not learn at all, and the ResNet runs were affected more mildly.

What happened: the first epoch's loss came out near 6.7, then dropped to 2.3026 and stayed there to four decimal places for as many epochs as it was given. That number is ln(10), the loss of a network producing identical logits for every input, so every class gets probability 0.1 and accuracy sits at exactly 10.0. The early Adam steps overshot into that flat basin and never climbed out.

The cause was applying He initialization to the classifier. He is derived for a hidden layer feeding a ReLU, where preserving the signal's scale is the point; on a layer whose outputs are logits it makes them far too large. The generated weights were in fact correctly He-scaled, measured at 0.015625 against sqrt(2/8192) = 0.015625, so this was not a broken implementation of the intended initialization. The intent was wrong for that one layer. The classifier now uses one over fan-in, which starts the logits near zero.

This is worth knowing rather than just fixing, because it says something about where hypernetworks are fragile. Plain backprop on the same 300 images reached about 30% throughout, and PyTorch's default Linear initialization is roughly 2.4 times smaller than He, which is why the direct baseline never hit this. The generated path had no such luck.

Check your earlier runs. If a learn request's final_loss is 2.3026 and its accuracy is exactly 10.0, that run hit this and its numbers are not usable. ResNet puts batch normalization before the classifier, which keeps the incoming features near unit scale, so those runs were less likely to collapse outright, but the initialization still changed, so they are not comparable with runs from after the fix.

What a run costs

Every request is timed, and on a GPU its peak memory is recorded around it. Learning and forgetting are very different jobs, so they are reported separately rather than averaged into one meaningless number. A finished run prints this:

The numbers above are made up to show the layout, not measured. The columns that matter:

  • prot is how many tasks the regularizer had to protect during that request. This is the column that explains the other two. Every protected task gets its weights regenerated inside the same graph, so both time and memory climb as the sequence goes on.
  • s/step makes learn and forget comparable. A learn step walks a batch of images through the generated network; a forget step touches no data at all. If a forget step is not clearly cheaper than a learn step, the regularizer is the cost, not the objective.
  • peak GiB is what decides whether request 29 survives. Watch whether it grows linearly with prot, which is the behaviour to expect.

It is all in the returned dict and on disk:

Four files per run, named for the sequence, backbone and seed: history_, summary_, costs_ and environment_. The environment file records the GPU, the torch and CUDA versions, the git commit and every Config field, so a number found months later can be traced back to the code that made it. History and costs are rewritten after every request.

Reading the four numbers

run_experiment returns a dict: history, numbers, costs, totals, environment and the config it used. Accuracy at the end hides the two failure modes the paper is about, which is why there are four.

RA
retain_accuracy — average over tasks still held at the end. Higher is better.
FA
forget_accuracy — average over forgotten tasks. Should sit at chance, 10%.
Spill
mean_spill — how much one forget request disturbed every other task. Lower is better.
Relapse
mean_relapse — how much a forgotten task crept back as later tasks were learned. Lower is better.

The paper reports 55.24% retained accuracy on Tiny ImageNet in Table 3, so that is the region to check against. history holds a record per request with before and after accuracy for every task seen so far, plus final_loss and the annealed burn_in that forget request used.

Both are plain JSON, so a finished or interrupted run reads back without rerunning anything:

Five things that will bite

  • Memory grows with history. The regularizer regenerates every protected task's weights in one graph, so by request 29 it is holding nineteen full sets of ResNet50 parameters at once. If a late request dies with a CUDA out-of-memory error while early ones were fine, that is why. Fewer chunks, a smaller batch_size, or ResNet18 are the levers.
  • Data loading is single-threaded. The loaders inside uncle/trainer.py use the default of zero workers, so JPEG decoding happens on the main process. At 5,000 images per task it is probably not the bottleneck, but if the GPU looks idle, that is the first place to look.
  • Accuracy here is validation accuracy. Tiny ImageNet's public test split has no labels, so the test slot holds val. Say so when you report a number.
  • Task IDs used to mean two different things. There were two Tiny ImageNet loaders with different class groupings, so task 3 named different classes depending on which one you went through. There is one now, on the seed-42 partition saved in uncle/task_partition.json and checked on every run. Numbers from before that merge are not comparable with numbers from after it.
  • A learn is not repeatable. The sequences never learn the same task twice and Config rejects it if you try. Relearning a forgotten task needs a separate adaptation path, which does not exist yet.
  • Sweeps used to overwrite each other. The output files are now named history_seq1_resnet50_seed0.json, carrying the sequence, backbone and seed, so a loop over seeds keeps all of its runs. Before that fix every run in a loop wrote the same filename and only the last one survived. Sweeping anything else, beta or gamma, still collides: use output=None and keep the returned numbers, or give each point its own directory.
  • The import path changed. There is one package now. Put the repository root on the path, not a subfolder, and import from uncle.experiments. The old uncle_from_scratch folder is gone: its data and task code moved into uncle/, its entry points into uncle/experiments.py and uncle/baseline.py, and there is no longer a second Tiny ImageNet loader with a different class grouping.

What the paper does, in one paragraph

One hypernetwork learns to produce the weights of a ResNet from a short code, one code per task. Learning task 3 trains the hypernetwork to turn code 3 into weights that classify task 3. Forgetting task 3 trains it to turn code 3 into noise instead, which needs no data at all: that is the whole point, because continual learning throws the old data away. A second term in both objectives holds every other task's generated weights where they already were.

Then the paper does one thing repeatedly: it writes down a random sequence of learn and unlearn requests, runs it, and measures what happened to every task. Everything else is a variation on that loop.

Fixed everywhere else: a fully connected hypernetwork with hidden layers 128, 256 and 512; 200 chunks per generated network; 32-number task and chunk codes; chunk codes frozen after the first task; one output head per parameter type; Adam at 0.001; gamma 0.01 (0.1 for 5-Tasks); ten noise samples; burn-in 100, annealed 10% per unlearn with a floor of 20. Everything ran on one V100.

Tiny ImageNet is 20 tasks, not 10. The paper's text says every dataset but 5-Tasks has ten tasks, but Table 4's Tiny ImageNet sequences name tasks up to 19, so the long run needs twenty. This code follows Table 4. It is the kind of gap worth knowing about before you build on the numbers.

The four numbers, and where they come from

RA
Average accuracy over the tasks still retained at the end of the sequence.
FA
Average accuracy over the forgotten tasks at the end. Ten percent is the target, because every task is ten-way.
Spill
Equation 4. After one unlearn, add up how much every other task's accuracy moved. Measures whether forgetting stayed in its lane.
Relapse
Equation 5. For each forgotten task, the gap between its accuracy right after it was forgotten and its accuracy at the end. Measures whether forgetting stuck.

The argument for having four is worth internalizing, because it is the paper's main contribution beyond the method. RA and FA are both measured only at the end, so they can be gamed by the order of the sequence: an unlearn as the last request drags RA down for everyone, and a run of learns at the end inflates FA. Spill and relapse are measured at the moment things happen, so they cannot be arranged away.

What you can reproduce with this code today

Every experiment below carries one of three labels:

runs today
The code already does this. Copy the command and go.
small addition
The experiment runs, but something it measures is not recorded, so you add a few lines in the notebook. Nothing here needs this any more: the two that did were both about timing, and uncle/telemetry.py now records that.
not implemented
Needs real code in the library, not notebook glue: editing the forget loop, or writing an attack from nothing.

Two gaps to know about before you start. This code has Permuted MNIST and Tiny ImageNet, so two of the paper's four dataset columns are out of reach. And none of the seven comparison methods in Table 1 exists here (BadTeacher, SCRUB, SalUn, JiT, GKT, SSD and CLPU), nor the extra ones in the appendices.

So: you can reproduce UnCLe's own row of every table, but not the comparison. That is less limiting than it sounds. Every ablation in the paper is UnCLe against itself, and those are the experiments that teach you how the method behaves. The baseline rows mostly establish that methods built for offline unlearning do badly in a continual setting, which is the paper's starting point rather than something you need to re-check.

1. The main comparison runs today

What happens One request sequence, run start to finish, three times with three different seeds. At the end, RA and FA over all tasks (Table 1), and spill and relapse averaged over the unlearn requests (Table 2).

Why This is the headline claim: UnCLe forgets completely and keeps the rest. The four numbers together are the evidence.

Watch for FA landing on 10.00 and staying there, and spill under one. Those are the two the paper wins on by a wide margin. Here are its numbers to check against:

Look at that Permuted MNIST relapse: 8.703, while SCRUB gets 0.149 and SSD 2.586 on the same dataset. The paper's own table shows relapse is the one metric where UnCLe is not comfortably ahead, and it is worst on the easiest dataset. That is a loose thread, and loose threads are where research starts.

2. One task's trajectory runs today

What happens Pick one task, plot its accuracy after every request in the sequence (Figures 2 and 4). You get a step up when it is learned, a flat stretch, a cliff down to 10% when it is unlearned, and a flat stretch at 10% after.

Why This is the picture the four numbers summarize. Baselines produce jagged lines: their forgotten tasks climb back up as later tasks are learned, and their retained tasks dip every time something else is unlearned. Seeing one clean staircase is more convincing than any table.

Watch for Whether the line stays flat between the green and red markers, and whether it stays flat after the red one. Any climb after the red marker is relapse, happening in front of you.

3. The beta search runs today

What happens Run the whole sequence four times, with beta at 1, 0.1, 0.01 and 0.001, and keep the value with the best average accuracy (Table 5).

Why Beta is the weight on the term that holds other tasks still. Too small and learning a new task wrecks the old ones; too large and the network cannot learn anything new. The paper calls this the stability and plasticity balance, and it is dataset-specific: the same sweep picks 0.1 for Permuted MNIST and 0.01 for Tiny ImageNet.

Watch for How flat the curve is. On Permuted MNIST the paper's four values span 96.24 to 96.68, which is nearly nothing. On Tiny ImageNet they span 8.49 to 53.74. The harder the dataset, the more this one number matters, and a sweep on Permuted MNIST tells you almost nothing about the setting you care about.

4. The gamma and burn-in search runs today

What happens Same idea for the two unlearning knobs. Gamma over 0.1, 0.01 and 0.001; burn-in fixed at 100 after finding it sufficient everywhere (Table 6).

Why The selection rule is the interesting part, and it is worth copying: first keep only the gamma values that drive FA to chance or below, then among those, pick the one with the highest RA. Forgetting is the requirement; retained accuracy is the thing you optimize subject to it. Tuning on a blend of the two would let a configuration that forgets badly win on average.

Watch for A detail the paper glosses over. On Permuted MNIST its own gamma table reports FA of 10.412, 10.417 and 17.907, so no value satisfies "FA at or below 10" and the rule has to become "closest to 10". Worth deciding explicitly what your own rule is before you run it, rather than after you see the numbers.

5. Burn-in annealing runs today

What happens Burn-in is how many optimizer steps one unlearn request gets. The paper starts at 100 and cuts it 10% after every unlearn, with a floor of 20, then checks that forgetting is just as complete and measures the time saved (Table 7). On Tiny ImageNet, average unlearning time went from 45.12 to 29.63 seconds with FA unchanged at 10.00.

Why It is a free efficiency win, and it tells you something about the method: later unlearns need fewer steps than earlier ones. The hypernetwork is getting better at forgetting as it goes, which is a real finding hiding inside an efficiency tweak.

Watch for The steps column for forget requests, which is the annealed burn-in: 100, 90, 81, 72 and so on down to the floor of 20. Check the seconds fall with it, and check FA really does stay at 10 as the budget shrinks, because that is the claim. Watch the s/step column too: if it climbs while steps falls, the regularizer is eating the saving, because it grows with the number of protected tasks.

6. Alternative noising strategies not implemented

What happens The forget objective asks the generated weights to match a Gaussian noise sample, averaged over ten fresh draws each step. Appendix E swaps that for three alternatives: one fixed noise sample reused throughout, plain shrinking of the weights toward zero, and simply throwing the task's code away and replacing it with a random one.

Why This is the most instructive part of the paper, because of Theorem 1. Averaging over n fresh zero-mean draws converges to the squared norm of the weights plus a constant, which is smallest at zero. So the objective does not randomize the weights: it drives them toward zero, which makes the forgotten task's outputs uniform across classes, which is maximum uncertainty. Ten samples is chosen as a middle point: one sample lets the network memorize that one draw, and infinitely many is plain norm reduction, which the paper reports destabilizes the hypernetwork.

Tiny ImageNet, sequence 1RAFA
Fixed noise, one draw reused34.689.44
Norm reduction55.1136.61
Discard the task's code56.5015.54
UnCLe, ten fresh draws55.2410.00

Watch for Fixed noise forgets fine but costs twenty points of retained accuracy; norm reduction keeps accuracy but barely forgets. Only the average of fresh draws gets both.

The trap. Setting noise_samples=1 here does not give you the paper's fixed-noise variant. This code draws a fresh sample every step, so n=1 is "one fresh draw per step", not "one draw reused forever". They behave completely differently: fresh draws still average toward zero over many steps, a reused draw does not. Reproducing Appendix E means editing the forget loop in uncle/trainer.py to sample once, outside the loop.

7. Saturation alleviation runs today

What happens Run the same sequence twice: once as written, and once with every unlearn request deleted. Compare final accuracy on the tasks that survive in both (Table 3, Figures 5 and 7). On Tiny ImageNet, learning only gets 50.47 and learning plus unlearning gets 55.24.

Why This is the paper's second, more surprising claim: forgetting is not only a privacy tool, it makes the model better at learning. A continual model fills up and loses the ability to take on anything new; returning a task's weights to something like a fresh initialization gives that capacity back. Note where the effect appears: almost nothing on Permuted MNIST (96.84 to 96.87) and 5-Tasks (94.12 to 94.12), clear gains on Tiny ImageNet and CIFAR-100. The easy datasets never fill up, so there is nothing to recover.

Watch for The comparison has to be on the same set of tasks. The learning-only run ends up holding all twenty tasks, including the ones the real run forgot, so comparing its average over twenty against the real run's average over six is meaningless. The paper's Figure 7 compares exactly the six tasks that survive sequence 1: T19, T13, T18, T2, T11 and T8. Take the retained list from the real run's last record and score both runs on that.

8. Membership inference not implemented

What happens An attacker tries to tell whether a given example was in the training data. 50% means they are guessing. UnCLe scores 50.00 on every dataset (Table 9).

Why It is the standard privacy check in the unlearning literature, so it has to be there. But read the paper's own explanation carefully: because each task has its own head and forgetting randomizes that head, every method scores about 50, and the paper says so outright. The metric cannot separate the methods in this setup. It is a box being ticked, not evidence, and that is useful to know if you were planning to lean on it.

Watch for If you build this, the interesting version is the one the paper does not run: attack the shared hypernetwork rather than the forgotten task's head. That is where residual information about a deleted task would have to live.

9. Unlearning time runs today

What happens Seconds per unlearn request, averaged over the sequence (Table 10). UnCLe takes 29.63 seconds on Tiny ImageNet against 147.5 for GKT and 65.20 for SalUn.

Why Unlearning that needs data or retraining is slow and awkward in a continual setting. This is the practical argument for a data-free method, and it is entirely controlled by burn-in.

Watch for The comparison is only fair on the same GPU. The paper's numbers are from a V100; a T4 is slower, so reproduce the shape, unlearning much cheaper than learning and getting cheaper as annealing kicks in, rather than the absolute seconds. The saved costs_ file holds every request, and the environment_ file records which GPU produced them, which is what makes two runs comparable at all.

10. Other sequences and other backbones runs today

What happens Everything above uses sequence 1. Appendix H repeats it for sequences 2 and 3, and swaps ResNet50 for ResNet18, all averaged over three seeds.

Why A method that only works on one ordering of requests has not been shown to work. This is the generalization check, and it is the cheapest real experiment in the paper to repeat.

Watch for That is eighteen full runs, so budget it before you start. And one oddity in the paper worth confirming: on CIFAR-100, ResNet18 gets a higher retained accuracy than ResNet50 (66.97 against 62.65). The bigger backbone is not automatically better here, which fits the saturation story: more parameters to generate is also more for one hypernetwork to hold still.

What the paper does not tell you

Four gaps, all of which you hit the moment you try to reproduce anything. Knowing them is the difference between "my numbers are wrong" and "these numbers were never pinned down".

  • Epochs, batch size and the learning rate schedule. The main text says these are deferred to Appendix C. Appendix C covers the request sequences, beta, gamma and burn-in, and never returns to them. So the training budget per learn request is unspecified, and it is one of the biggest levers on RA.
  • The UNI metric. Appendix E reports a column called UNI, with values like 100.0 for UnCLe and negative infinity for fixed noise, and it is never defined anywhere in the paper. From context it measures how uniform the forgotten task's output distribution is, but you cannot reproduce a number whose formula is missing.
  • Which classes make up each task. For Tiny ImageNet and CIFAR-100, the grouping and ordering of classes is never given. This code shuffles with a fixed seed and saves the result, which makes it reproducible but not the paper's.
  • Hyperfan initialization. The paper initializes the hypernetwork so the generated network comes out Kaiming He initialized. This code uses Kaiming initialization with output scaling instead, which is the same intent by a simpler route, but it is not the same thing.

A suggested order

If the goal is to be fluent in this before starting your own work, the cheap experiments teach the most per hour:

  • Experiment 2 first, on a small ResNet18 run. One picture of one task's staircase and you understand spill and relapse permanently.
  • Then experiment 7, saturation. It is the paper's most interesting claim, it needs no new code, and setting up the matched comparison teaches you what the request sequence actually does.
  • Then experiment 4, the gamma search, because the selection rule is the part of the method most likely to be wrong in your own work.
  • Then experiment 1 at full scale, once, so you have one honest reference run of your own.
  • Leave 6 and 8 until you need them. They need new code, and 8 in particular cannot distinguish anything in this setup.
