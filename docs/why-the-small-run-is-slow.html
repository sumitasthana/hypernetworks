Diagnosis of the local implementation · September 21, 2026

Why this small UnCLe run can take so long

The largest hidden startup cost is the dataset loader. Your max_images=300 limit is applied after the full training and validation datasets have been indexed. That indexing happens before the experiment's progress bar appears. If you are already seeing training progress, the 100-step forgetting request, repeated evaluation, and compute device become the relevant suspects.

I inspected the code and measured dataset setup on the local checkout. I cannot identify the bottleneck in your running notebook without its last displayed output and the value of DATA. The findings below distinguish measured behavior from possible explanations.

1. Your call is larger than it looks

This is four distinct tasks, each with 300 training images and 300 validation images after capping. max_images is a per-task, per-split cap, not a limit of 300 images for the whole run.

At the default batch size of 64, one learning epoch is five updates. But epochs=1 does not reduce forgetting: that uses burn_in=100 independently. These steps have different costs, so their counts are not a runtime estimate.

The 20 evaluation passes process 6,000 validation-image instances. Learning processes another 1,200 training-image instances. The loader opens and decodes images on demand without a decoded-image cache. Evaluation includes forgotten tasks and repeats the previous request's final evaluation before the next request.

Sources: config.py, experiment.py, trainer.py.

2. The cap does not make dataset setup small

The actual startup order is:

run_experiment()
  build_tasks()
    prepare_data()                  # download/extract if markers are missing
    TinyImageNet(..., "train")       # index every training class
    TinyImageNet(..., "val")         # index the full validation split
    ClassTask(...)                  # select the requested class groups
    _capped(..., max_images=300)     # only now apply your limit
  create progress bar and start experiment timer
  build models and print environment
  run the requests

The training index reads class manifests and checks individual paths, including repeated Path.is_file() calls. The validation loader also checks candidate paths for every validation image. Selecting just four tasks does not avoid construction of these full base datasets.

Local measurement: dataset construction for your exact four tasks and 300-image cap made 220,200 calls to Path.is_file() and took 9.43 seconds on this checkout. This included a lightweight call-counting wrapper; it excluded imports, downloading, model construction, and training. All eight capped splits contained 300 images. This is a local measurement, not a prediction for your notebook.

If DATA points to a mounted or remote filesystem, this number of small file checks is a plausible reason for a long silent wait. A fresh download also extracts the full archive; the image cap does not reduce the download or extraction.

download=True does not unconditionally redownload. It checks four marker paths first. Those markers are not a full integrity check: a partially extracted dataset can have the markers and still fail later when individual images are checked.

Reducing epochs, max_images, or limit_requests does not remove this full-dataset indexing stage. Also, the reported experiment time starts afterward, so it omits this initial delay.

Sources: experiments.py, streams.py, tinyimagenet.py.

3. A small classifier still has a larger generator

I instantiated your model configuration locally. The CNN has 87,018 generated parameters, while the hypernetwork has 1,569,312 parameters before task codes are added. Choosing backbone="cnn" does not remove the hypernetwork, whose default hidden widths remain (128, 256, 512).

Each update generates the current task's weights. For every protected task, it also generates both current weights and frozen-reference weights. The frozen reference is recomputed every step, even though it stays constant within a request. During forgetting, each step additionally computes ten noise-comparison losses over the generated parameter vector.

The default device is CUDA when available, otherwise CPU. Your call does not require a GPU, so it can silently run on CPU. My inspection environment is CPU-only; that says nothing about your notebook's hardware. Image loading is also serial in these DataLoaders, so a GPU does not solve slow image access.

Do not assume that reducing chunks always reduces model size: fewer chunks require a wider output head to generate the same number of classifier weights. Its effect on speed is a tradeoff that needs measurement.

Sources: hypernet.py, trainer.py, config.py.

5. Two useful notebook checks

Run this in the notebook environment that is slow:

from pathlib import Path
import torch
import uncle.experiments as experiments

print("Imported code:", experiments.__file__, flush=True)
print("DATA:", Path(DATA).expanduser().resolve(), flush=True)
print("CUDA available:", torch.cuda.is_available(), flush=True)
print("CPU threads:", torch.get_num_threads(), flush=True)
if torch.cuda.is_available():
    print("GPU:", torch.cuda.get_device_name(0), flush=True)

If you need to locate a silent wait, interrupt the existing run first, then wrap the call with periodic Python stack reporting. This starts a new run; it does not resume the interrupted one.

import faulthandler
from time import perf_counter

faulthandler.enable()
faulthandler.dump_traceback_later(30, repeat=True)
started = perf_counter()
try:
    result = experiments.run_experiment(
        sequence=1, backbone="cnn", chunks=32, epochs=1,
        limit_requests=5, max_images=300,
        root=DATA, download=True,
    )
finally:
    faulthandler.cancel_dump_traceback_later()
    print("Total wall time:", round(perf_counter() - started, 1), "seconds")

A stack in tinyimagenet.py, filesystem checks, or extraction points to setup. A stack in image loading or accuracy() points to evaluation/input work. A stack in forget(), preserve(), or backward computation points to model updates. Stack reports locate the active phase; they do not measure GPU kernel time.

6. What to change first

If this is Colab and DATA is on mounted Drive: use an explicit runtime-local dataset path, such as /content/data/tiny-imagenet-200, and keep saved results on Drive. The repository's Colab guide already uses this layout. Leaving root out is only helpful if the clone itself is on local storage.

DATA = "/content/data/tiny-imagenet-200"
# Rerun with root=DATA and download=True to prepare this local copy.

If the delay is model computation: first confirm the intended GPU is active. For a deliberately smaller execution check, the following reduces both generator size and the forgetting budget. Its learning and forgetting results are not comparable to your original configuration.

result = experiments.run_experiment(
    sequence=1,
    backbone="cnn",
    chunks=32,
    hidden=(32, 64),
    epochs=1,
    limit_requests=3,   # learn 3, learn 0, forget 3
    max_images=50,
    burn_in=5,
    burn_in_min=5,      # otherwise the default floor raises it to 20
    root=DATA,
    download=True,
)

This smaller check still pays the full indexing cost. For a GPU-only check, add device="cuda"; this will fail if CUDA is unavailable instead of falling back to CPU.

Changes the implementation could make

To improve the existing run without simply weakening its experiment, the relevant changes are: index only requested classes and capped images, report progress and timing during setup/evaluation, cache frozen-reference weights within a request when memory permits, and reuse the previous post-request accuracies as the next pre-request accuracies. These are potential code changes, not changes made during this investigation.

Scope: source inspection, exact model-size calculation, and a measured local dataset build. No full training benchmark was run, and no training or loader code was modified. The Colab guide's “finishes in minutes” description is not a hardware-independent guarantee.
